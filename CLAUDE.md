# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Laravel + Inertia.js + React (TypeScript) app for monitoring and managing Perusahaan Jasa Pertambangan (PJP — mining services companies) across three aspects that apply to **every** PJP at once, not sequential stages a company progresses through:

1. Persyaratan, Seleksi, dan Penetapan (`persyaratan-seleksi-penetapan`) — SMKP prequalification checklist score
2. Tanggung Jawab, Pemantauan, dan Pelaporan (`tanggung-jawab-pemantauan-pelaporan`) — reporting compliance score
3. Evaluasi (`evaluasi`) — semesterly performance evaluation score

Each of these 3 pages lists **every** registered PJP, showing that page's own score for each one. This used to be a per-PJP `tahapan` column gating which single page a PJP appeared on, with a "Lanjutkan ke Tahap Berikutnya" button to move between them — that concept was deliberately removed (the `tahapan` column, `Pjp::TAHAPAN`/`NEXT_TAHAPAN`, `PjpController::advanceTahapan`, and the "Tahapan" field on the Create/Edit form are all gone) because these three aspects are independent and can be filled in at any time for any PJP; a checklist, a laporan, and an evaluasi for the same company don't have to happen in any particular order. See **Achievement chart / composite score** below for how a single cross-page score is still derived when one is needed (Beranda's "Perlu Perhatian" widget, the sidebar badge).

There is no authentication yet — every route is publicly accessible. This is a known, deliberate gap (see git history), and is explicitly the **last** feature to be built, not the next one — deferred on purpose because the intended design is per-kontraktor login registered by email (each PJP/kontraktor gets its own account tied to their email, scoping their access to just their own checklist/laporan uploads instead of today's guess-the-ID links), and that email-registration piece isn't ready to design yet. Don't jump ahead and build a generic login system before that's revisited — check with the user first if auth ever seems like the natural next step.

## Working with this project's maintainer

The maintainer runs terminal commands manually on their own Windows laptop (VS Code's integrated terminal), not through an automated tool — so when giving them shell/terminal commands to run, send them **one command at a time**, not as a combined multi-line block. Explain what the command does, wait for them to run it and report back (or share the output), then give the next one. This applies whenever commands are meant for *them* to type, not to commands you run yourself in your own sandboxed session.

## Commands

```bash
composer install
npm install
cp .env.example .env
php artisan key:generate
touch database/database.sqlite
php artisan migrate
php artisan storage:link   # required for uploaded PJP documents to be servable
```

Run backend + Vite together:

```bash
composer run dev
```

Or separately:

```bash
php artisan serve
npm run dev       # dev server with HMR
npm run build     # production build (also run this to sanity-check before committing)
```

Tests: `composer test` (aliases `php artisan config:clear && php artisan test`) or `php artisan test --filter=TestName` for a single test. `tests/Feature/` covers the business rules most prone to silent regression (see below); `Pjp`, `PjpLaporan`, and `PjpEvaluasi` all use `HasFactory` (`database/factories/*Factory.php`) to support this.

Type-check the frontend (no separate script defined): `npx tsc --noEmit`.

PHP lint a single file: `php -l path/to/File.php`.

## Architecture

**Data model**: two Eloquent models carry the whole domain.

- `App\Models\Pjp` — a company record. Notable statics: `Pjp::STATUS` is the canonical label map (keys are the DB values: `aktif`, `perlu_tindak_lanjut`, `tidak_aktif`); `Pjp::statusCountsFor(?Builder $query)` returns status→count always including every status key; `scopeFilter($search, $status)` is the shared search/filter query logic used by both `PjpController` and `TahapanController` — extend this scope rather than re-adding `->when(...)` chains in a controller.
- `App\Models\PjpLaporan` — an uploaded compliance document belonging to a `Pjp` (`belongsTo`), one of four `jenis` (`PjpLaporan::JENIS`: `spip`, `tsp`, `laporan_bulanan`, `laporan_triwulan`). Business rules live here as model constants/methods, not in the controller:
  - `BATAS_TANGGAL_LAPORAN = 3` — every document type is "tepat waktu" (on time) only if uploaded on or before the 3rd of the month; this is a computed `tepat_waktu` accessor (always present via `$appends`), not a stored column.
  - `BULAN_TRIWULAN_DIBUKA` — Laporan Triwulan can only be uploaded in April/July/October/January (TW1–TW4); `PjpLaporan::triwulanSedangDibuka()` gates the upload endpoint (`PjpLaporanController::store` rejects uploads outside the window) and also drives the frontend (`PjpController::show` passes `triwulanTerbuka` so the upload form is hidden client-side too — both checks must stay in sync if this rule changes).
  - `kesesuaian_isi` (`PjpLaporan::KESESUAIAN`: `sesuai` / `tidak_sesuai` / null) is a manual reviewer judgment set via `PjpLaporanController::update`, independent of the automatic `tepat_waktu` flag.

**Checklist prakualifikasi SMKP** (halaman Persyaratan): `App\Models\SmkpChecklistCategory` (17 rows: `LEGALITAS` + `A`-`P`) and `SmkpChecklistItem` (126 leaf questions, each with a fixed `bobot`) are reference/lookup data seeded once by the data migration `2026_09_07_040003_seed_smkp_checklist_data` from `database/seeders/data/smkp-checklist.json` (parsed from the source prequalification Excel — company branding stripped, "SMK3PLM"/"SMKPLH" normalized to "SMKP") — treat this as fixed reference data, not something to reseed via `db:seed`. `SmkpChecklistAnswer` holds one row per `(pjp_id, smkp_checklist_item_id)` with `jawaban` (Y/T/N/A) and `nilai` (`0`-`3`/`na`), filled in by the PJP itself via `GET|POST /pjp/{pjp}/checklist-smkp` (`SmkpChecklistController`, page `Pjp/ChecklistSmkp.tsx`) — there's no PJP login, so anyone with the link can fill it in, consistent with the rest of the app being unauthenticated. `Pjp::smkpScore()` computes the weighted percentage from answered items (an item with `nilai = 'na'` is excluded from both the score and its bobot denominator; an unanswered item still counts toward the denominator at 0) and maps it to a `kategori_risiko` band (Kritis/Tinggi/Sedang/Rendah/Sangat Rendah — the source document's bands describe the minimum score needed to qualify for a given job-risk level, not the PJP's own riskiness) — the `LEGALITAS` category is a separate pass/fail gate and is excluded from this score entirely. `TahapanController::renderTahapan` attaches `smkpScore` to each PJP only on the `persyaratan-seleksi-penetapan` page, where `PjpMiniList` renders it as a percentage badge.

**Evaluasi kinerja**: `App\Models\PjpEvaluasi` is one row per `(pjp_id, tahun, semester)` (`PjpEvaluasi::SEMESTER`: `1` = Jan-Jun, `2` = Jul-Dec), holding three independent 0-100 scores — `skor_teknis`, `skor_keselamatan_kesehatan`, `skor_lingkungan` — plus a computed `skor_rata_rata` accessor (simple mean of the three, always appended). `PjpEvaluasiController::store` (`POST /pjp/{pjp}/evaluasi`) is an `updateOrCreate` keyed on `(pjp_id, tahun, semester)`, so resubmitting the same semester overwrites it rather than erroring or duplicating — there's no separate edit endpoint. The form (`EvaluasiCard.tsx`) is embedded unconditionally on `Pjp/Show.tsx`, same as the Persyaratan PJP checklist button — there's no per-PJP gating of any kind, evaluation history can always be recorded for any PJP. `TahapanController::renderTahapan` attaches each PJP's single latest `PjpEvaluasi` (or explicit `null`) as `latestEvaluasi` only on the `evaluasi` page, and `PjpMiniList` renders it as a badge (distinguishing "no evaluation yet" from an evaluation scored 0).

**Achievement chart / composite score**: each of the 3 pages (Persyaratan/Tanggung Jawab/Evaluasi) renders an `AchievementBarChart` listing **every** PJP — a horizontal bar per PJP, sorted ascending (lowest/most-needs-follow-up first), colored by a fixed 4-band status scale (good/warning/serious/critical, same hex steps as `StatusStackedBar`'s status colors). `TahapanController::renderTahapan` picks which score becomes each row's `achievement` value based on which page is being rendered — `Pjp::smkpScore()['persentase']` on the Persyaratan page, `Pjp::pelaporanScore()` on Tanggung Jawab (`null`, not a colored 0%, when the PJP hasn't uploaded anything yet — a distinct muted "belum ada laporan" row), and the latest `PjpEvaluasi::skor_rata_rata` on Evaluasi — this is a per-page value, not a property of the PJP itself, since every PJP appears on all three pages simultaneously. `Pjp::achievement()` is a *different*, composite score used only where a single cross-page number is needed (Beranda's "PJP Paling Perlu Perhatian" widget, the sidebar's "Perlu Perhatian" badge via `perluPerhatianCount()`): it's the **minimum** of whichever of the three metrics are non-null (SMKP score is always numeric — an empty checklist is 0%, not null — while pelaporan/evaluasi genuinely can be null when nothing's been submitted yet and get excluded rather than treated as 0). Minimum, not average, so one badly-scoring aspect isn't hidden by two good ones. Each achievement-chart row links to `/pjp/{id}` by default — the chart doubles as a "who needs follow-up" worklist, not just a summary. `AchievementBarChart` takes an optional `hrefFor(item)` to override that per page; the Persyaratan page is the one that does, pointing straight at `/pjp/{id}/checklist-smkp` instead, since that chart is specifically about the SMKP checklist and there's no reason to make the reader pass through the general detail page first.

**SMKP donuts on `Pjp/ChecklistSmkp.tsx`**: two distinct donut visuals, both on the same page, both clickable — neither is a categorical multi-series chart, so neither needs the dataviz skill's palette validator (each is a single-value "meter": achieved-vs-gap, colored by the same 4-band achievement scale as everywhere else, unfilled portion in a neutral slate track).
- **"Kelengkapan Checklist"** (`SmkpDonutChart`): one big two-arc donut of the overall `score.persentase`, plus two clickable summary rows below it that go to two *different* places on purpose — "Sudah lengkap" scrolls to the `#rincian-skor-kategori` card, "Belum lengkap" finds the single lowest-scoring category from `categoryBreakdown` and jumps straight to it (see below) — a direct path from "something's dragging the score down" to "here's the exact form to fix it," not just more reading.
- **"Rincian Skor per Kategori"**: what used to be a `space-y-2` list of linear bars (one per A-P category) is now a `grid` of small per-category donuts (`CategoryDonut`, defined in the same file) — deliberately "many small donuts" rather than one chart, since each category's completion is its own independent, clickable fact, not a breakdown of one whole. Every donut is its own `<button>`; clicking it calls the same `openCategory(kode)` helper the "Belum lengkap" row above uses.
- Both click paths funnel through `openCategory(kode)`: `document.getElementById(`kategori-${kode}`)`, force `el.open = true` (the category `<details>` elements aren't otherwise stateful/controlled), then `scrollIntoView({ behavior: 'smooth' })` — plain DOM, not routing, since donut and target are on the same page. This only works because every `<details>` in the category `.map()` carries `id={`kategori-${category.kode}`}`; don't drop that id if the accordion markup is ever restructured.
- The Persyaratan tahap page (`PersyaratanSeleksiPenetapan.tsx`) doesn't have any donut at all — clicking a company row there navigates straight to its `Pjp/ChecklistSmkp.tsx` via `AchievementBarChart`'s `hrefFor` override (`/pjp/{id}/checklist-smkp` instead of the default `/pjp/{id}`), and the donuts live entirely on the page it lands on. Two earlier rounds of this feature (an `onItemClick` popup on the list page, then a single donut for the whole category breakdown) were corrections en route to this — if the shape of "the donut chart" is ever revisited, confirm exactly which of these two on-page donuts before touching either.

**Automated test coverage**: `tests/Feature/` locks in the business rules that are easy to break silently (i.e. without `tsc`/lint catching it). `AchievementTest` covers both `Pjp::achievement()`'s min-of-available-scores composite logic (including that an empty SMKP checklist contributes 0.0, not null, so achievement is never null in practice) and, per tahap page, that `TahapanController` attaches the correct page-specific score as `achievement` for every PJP — a direct regression test for a past bug where `pjpsForTahapan`'s `->get(['id', 'nama_perusahaan', 'status'])` silently dropped the (since-removed) `tahapan` column that `achievement()` used to switch on, making every row look like "no data" instead of its real score; that whole bug class is gone now that `achievement()` no longer depends on any column beyond `id`, but the endpoint-level regression tests stayed to guard the current per-page attachment logic the same way. Other suites: `SmkpScoreTest` (weighted score math, `na` exclusion, unanswered-still-counts-toward-denominator), `PelaporanScoreTest` (tepat-waktu/kesesuaian averaging, `null` vs `0`), `PjpLaporanTest` (the day-≤3 "tepat waktu" boundary, the triwulan month whitelist, and the upload endpoint actually rejecting/accepting based on it), `PjpEvaluasiTest` (the `updateOrCreate` overwrite-not-duplicate behavior keyed on `(tahun, semester)`), `PjpDestroyTest` (storage subdirectory actually gets deleted), and `PjpExportTest` (the Excel zero-as-blank-cell string-cast gotcha stays a string). When changing any of these behaviors, update the corresponding test rather than deleting it — they exist specifically because these rules aren't visible from the type system.

**`AchievementBarChart` / SMKP category breakdown responsive layout**: both render a label + horizontal bar + value per row using fixed-width Tailwind classes (`w-64`, `w-28`, etc.) for the label/value columns so the bar's `flex-1` track lines up across rows — those fixed widths were sized for desktop only. On a ~390px mobile viewport the label+value alone exceed the available row width, so the `flex-1` bar shrinks to 0 and silently disappears (no console error, no layout break visible in a quick look — only obvious by actually measuring the rendered bar's width, e.g. via `getBoundingClientRect()`). The fix is a `flex-col sm:flex-row` row: mobile stacks label+value on one line and the full-width bar on the next; `sm:` restores the original fixed-width single-row layout unchanged. Any new label+bar+value row follows this same two-breakpoint pattern rather than a single fixed-width flex row. The label itself deliberately does **not** use `truncate`: real company/category names (e.g. "PT Borneo Tambang Sejahtera", "PERATURAN PERUNDANGAN DAN PERSYARATAN LAINNYA (P3L)") routinely exceed even a generously-sized fixed column, and silently cutting off a name with `...` is worse than letting it wrap to a second line — so the label column width is sized for the *common* case and left to wrap, never to truncate, for the long tail.

**Mobile header-row wrapping**: several page headers pair a heading/title with an action element (buttons, a link) in a single `flex items-center justify-between` row sized for desktop, with `shrink-0` on the action side so it keeps its natural width. On a ~390px viewport this silently overflows the viewport (`Pjp/Show.tsx`'s "Persyaratan PJP / Export PDF / Ubah Data / Hapus" button row, `Pjp/Index.tsx`'s "Export Excel / + Tambah PJP" row) or squeezes the heading into an ugly two-line wrap next to the action text (`AchievementBarChart`'s title+subtitle, `TahapanPjpSection`'s "Daftar Seluruh PJP" + "+ Tambah PJP", `PjpMiniList`'s per-row name+badges). None of this shows up as a console error or a broken build — only as clipped/overlapping text on an actual narrow viewport. The fix in every case is the same `flex-col sm:flex-row` stacking pattern (dropping `shrink-0` down to a `sm:` breakpoint too, e.g. `w-full sm:w-auto sm:shrink-0`), not a one-off tweak — any new header/action-row pairing should default to stacking on mobile rather than assuming it'll fit on one line.

**SMKP score drill-down**: `Pjp::smkpCategoryBreakdown()` returns the same weighted-score calculation as `smkpScore()` but per category (A-P) instead of one total — shown as mini bars on `Pjp/ChecklistSmkp.tsx` so it's obvious which category is dragging the score down, not just the overall percentage. `Pjp::smkpLegalitasStatus()` is a separate `{total, lengkap}` count of the `LEGALITAS` category's items answered `jawaban === 'ya'` (a plain completion count, not a 0-3 score like the rest of the checklist) — shown as a badge on both `ChecklistSmkp.tsx` and `Pjp/Show.tsx`, since Dokumen Legalitas is a pass/fail gate outside the 178-point score.

**Beranda stat cards**: `HomeController` passes all three `Pjp::STATUS` counts (`aktifDipantau`, `perluTindakLanjut`, `tidakAktif`) plus `total`, and `Home.tsx` renders one `GradientStatCard` per status (`sm:grid-cols-2 lg:grid-cols-4`) — deliberately all three, not just the two "actionable" ones, so `total` always equals the sum of the visible cards instead of silently including a status nobody can see on this page (this was a real point of confusion: total showing 7 while only two cards summed to 6 looked like a bug). The "Tidak Aktif" card uses a new `slate` gradient option in `GradientStatCard`'s `GRADIENTS` map and a new `inactive` (circle-with-X) icon in `TahapIcons.tsx`, distinct from the blue/green/amber trio already used for total/aktif/perlu-tindak-lanjut — it deliberately doesn't reuse red/amber since "tidak aktif" (no longer engaged) isn't a warning state the way "perlu tindak lanjut" is.

**Excel export gotcha**: `PjpExport::map()` deliberately renders every score column as a **string** (`'1.5%'`, not the raw float `1.5`) — PhpSpreadsheet/maatwebsite writes a literal numeric `0` as a blank cell (indistinguishable from a genuinely missing value once opened), so a PJP that legitimately scored 0% would render as an empty cell instead of "0%". Casting to string sidesteps this; don't change these back to raw numbers without re-checking that a real zero survives the round-trip.

**Sidebar summary widget**: `HandleInertiaRequests::share()` adds a `sidebarStats` prop (`{total, perluPerhatian}`, both lazy closures) to *every* Inertia response, not just Home's — it's how `Sidebar.tsx` shows a live "Total PJP" + "Perlu Perhatian" badge (linking to `/`) on every page without each controller having to remember to pass it. `Pjp::perluPerhatianCount()` reuses `Pjp::achievement()` the same way `HomeController`'s "PJP Paling Perlu Perhatian" list does, so the sidebar badge count and the Beranda widget never disagree. The `<aside>` is `sticky top-0 h-screen overflow-y-auto` — without that it stretches to match `<main>`'s height (flexbox default `align-items: stretch` on the `flex md:flex-row` root in `AppLayout`), which on any page taller than one screen pushed this widget and the footer off-screen at the bottom of the whole page instead of staying pinned in the visible sidebar.

**Bantuan (Help/FAQ) page**: `GET /bantuan` renders `Bantuan.tsx` — a static accordion FAQ (`<details>/<summary>`, same pattern as the checklist category sections) with a hardcoded array of question/answer pairs covering the SMKP checklist, why one PJP shows up on all 3 pages at once, Tanggung Jawab reporting rules, Evaluasi Kinerja, achievement chart colors, and exports. No controller/model backing it — the route closure renders the page directly. Linked from `Sidebar.tsx` as a standalone item (its own `help` icon in `TahapIcons.tsx`) below the nav list and `SidebarSummary`, not part of `navItems`, since it's reference material rather than one of the 3 pages.

**Global interaction feedback**: `PageProgress.tsx` (mounted once in `AppLayout`) listens to Inertia's `router.on('start'/'finish')` to show a thin blue bar at the very top of the viewport during navigation — without it, a slow page transition looks identical to a hung app, since Inertia swaps content in-place with no browser reload/spinner of its own. `ConfirmDialog` and `FlashMessage` both animate rather than snapping in/out (`pop-in` + backdrop fade for the dialog; `fade-in-up` in and a manual `leaving` state that fades/slides up before actually unmounting for the flash message, since a plain `if (!x) return null` can't play an exit transition). Every primary form-submit button (`Create`/`Edit`'s Simpan, `LaporanUploadCard`'s Unggah, `EvaluasiCard`'s Simpan Evaluasi, `ChecklistSmkp`'s Simpan Checklist) shows a small spinning `Spinner.tsx` next to the label while `processing` is true, on top of the existing `disabled`/`opacity-50` state — the disabled+dim state alone reads as "broken button" more than "working on it." `Pjp/Index.tsx`'s table rows and mobile cards got the same `row-in` stagger + hover highlight already used by `PjpMiniList`/`AchievementBarChart`, since they'd been missed when that treatment was first added elsewhere.

**`position: fixed` modals must not sit under a transformed ancestor**: `AppLayout.tsx` wraps every page's content in `<div className="page-enter">`, and `.page-enter`'s entrance animation used to run with `animation-fill-mode: both` — which keeps the *last* keyframe's `transform` (`translateY(0) scale(1)`) as the element's permanent computed style even after the animation finishes. That's visually a no-op, but a non-`none` `transform` on an ancestor makes it a new containing block for any `position: fixed` descendant (CSS spec, not a bug in one browser) — so every full-page modal rendered inside a page component (`ConfirmDialog`, `AchievementDonutModal`) was actually positioning itself relative to that content `<div>` instead of the viewport, silently landing in the wrong place on any page taller than the viewport (correct-looking only by coincidence on short pages, which is why this went unnoticed through several rounds of `ConfirmDialog` screenshots). Fixed by dropping the `both` fill-mode from `.page-enter` (`resources/css/app.css`) — the animation still plays the same on entry, but once it ends the element's computed `transform` reverts to `none` from the stylesheet instead of staying "stuck" at the animated end-state. Any future keyframe applied to an element that will contain a `position: fixed` child must avoid `forwards`/`both` fill-mode for the same reason, or the modal needs to escape via a portal instead.

**Custom error pages**: `bootstrap/app.php`'s `withExceptions()` registers an `Exceptions::respond()` callback that renders `Pages/Error.tsx` (inside `AppLayout`, so the sidebar/nav stays usable) for 404/403/419/429/405 unconditionally, and for 500/503 only when `config('app.debug')` is off — genuine 500s still show the full Whoops/Ignition trace during local development, since that's needed to actually debug them, while the always-safe 4xx codes (no debug info to lose) get the branded page even in local dev so they're not invisible during normal usage. `Error.tsx` maps `status` to an Indonesian title/description via a lookup object and always offers a "Kembali ke Beranda" link. JSON/API requests are excluded via the same `expectsJson()`/`api/*` check already used by `shouldRenderJsonWhen()`, so this never intercepts a non-HTML client.

**Cross-PJP evaluasi trend comparison**: `TahapanController::renderTahapan` attaches `evaluasiHistory` (every `PjpEvaluasi` row for that PJP, sorted chronologically ascending by `(tahun, semester)` — the reverse of the `evaluasis()` relation's own default descending order, which is right for "latest first" lists but wrong for a left-to-right timeline) only on the `evaluasi` tahap page. `EvaluasiTrendComparison.tsx` renders one line per PJP on a shared 0-100 axis, X-axis positions built from the *union* of every PJP's `(tahun, semester)` periods (not a fixed calendar range), so a PJP with only one evaluasi renders as a single dot (no line) rather than erroring or being skipped. Colors come from the dataviz skill's 8-slot categorical palette in fixed order (never cycled) — deliberately distinct hexes from the 4-color status/achievement palette used everywhere else in the app (good/warning/serious/critical), so a line color is never mistaken for a status. A 9th+ PJP folds into a muted "+N PJP lainnya" legend note rather than reusing a hue. Per-point hover detail rides a plain SVG `<title>` (matching the lightweight-tooltip convention already used elsewhere in this app, e.g. `AchievementBarChart`'s row `title` attr) rather than a custom tooltip component.

**Glassmorphism visual language**: every card that used to be `rounded-xl border border-slate-200 bg-white` is now the shared `.glass-card` CSS class (`resources/css/app.css`) — a translucent `rgba(255,255,255,0.62)` panel with `backdrop-filter: blur(24px) saturate(180%)`, a soft white border, a diffused shadow, and a bigger `1.25rem` radius. Empty/placeholder states use `.glass-empty` (dashed border, more transparent, no shadow) to keep that "nothing here yet" meaning distinct from a real content card. `AppLayout.tsx` renders 5 large blurred color blobs in a `fixed` (not `absolute`) `-z-10` layer behind everything — **this is not decorative filler, it's structurally required**: `backdrop-filter: blur()` on a `.glass-card` has nothing to blur without color behind it, so removing the blobs (or their opacity — they're intentionally strong, `/35` to `/60`) makes every glass card silently degrade into a flat semi-transparent gray box. Because the blobs are `fixed`, they stay put in the viewport as the page scrolls (by design — this reads correctly in a live browser; a Playwright *full-page* screenshot will only show them near the top of the capture, which is a screenshot-stitching artifact, not a bug in the page itself — verify by scrolling a real viewport-sized screenshot instead). `Sidebar.tsx`'s `<aside>`, its mobile `<header>`, and the mobile drawer all use `.glass-nav` (same blur, more opaque, no shadow — a nav surface, not a floating card) so the sidebar is part of this system too, not a leftover solid-white holdout. `GradientStatCard` and the amber warning/reminder boxes (`Home.tsx`'s "belum lapor" banner, `Show.tsx`'s catatan box) deliberately do **not** use `.glass-card` — they keep their own saturated color identity (gradient hero stat vs. glass content card vs. amber alert are three intentionally different surface types, not an oversight to "fix" into one look).

**Chart depth/glow treatment**: every bar/line chart got a matching upgrade so they don't read as flatter than the glass cards now wrapping them. Bars (`AchievementBarChart`, `StatusStackedBar`, `ChecklistSmkp`'s category breakdown) went from a flat `backgroundColor` fill to a `linear-gradient(90deg, <lighter tone>, <band color>)` plus a `boxShadow: 0 0 Npx 0 <band color>66` glow — each band/status color got a matching lighter "from" tone (e.g. good `#0ca30c` → `#4ade80`) defined right next to the existing fill map, so this is a from/to pair per color, not a generic brightness filter. Line charts (`EvaluasiCard`'s `TrenEvaluasi`, `EvaluasiTrendComparison`) got an SVG `drop-shadow` filter on the stroke/markers, and the single-line `TrenEvaluasi` additionally got a filled area under the line (`<linearGradient>` fading the line's own hue from ~35% to 0% opacity, closed into a `<polygon>` down to the baseline) per the dataviz skill's area-fill mark spec. `EvaluasiTrendComparison` deliberately does **not** get an area fill despite being a line chart too — with up to 8 overlapping series, stacked/overlapping translucent areas would muddy each other; the plain-line-plus-glow treatment there stays legible instead. Status/achievement colors are still the same reserved hex values from `references/palette.md`'s status palette — only a lighter *gradient partner* was added per color, the base semantic hex never changed.

**Micro-interaction / animation polish**: beyond the entrance animations from earlier rounds (`fade-in-up`, `pop-in`, `row-in`, `slide-in-left`), `resources/css/app.css` has a few more targeted keyframes, each reserved for a specific meaning rather than applied generically:
- `.pulse-ring` (amber pulsing box-shadow ring) is reserved for icons that mean "this needs attention *right now*" — the Sidebar's "Perlu Perhatian" badge and `Home.tsx`'s "belum lapor" reminder icon are the only two uses. Don't spread it to other amber icons/badges; it's meant to pull the eye to exactly these two spots, and loses that if every amber icon pulses.
- `.breathe` (subtle `scale(1.08) rotate(3deg)` loop) is for large watermark icons only (`GradientStatCard`'s big background icon). It deliberately animates only `transform`, never `opacity` — the watermark is already faded via a Tailwind alpha utility (`text-white/15`), and animating `opacity` on top of that would multiply the two alpha channels together (e.g. `0.15 × 0.15 ≈ 0.02`), making the icon nearly invisible at the low point of the loop instead of just dimmer.
- `.page-enter` (wraps every page's content in `AppLayout.tsx`) now runs the `page-in` keyframe (fade + `translateY(8px)→0` + `scale(0.99)→1`) instead of the older plain `fade-in-up`, so page transitions read as a soft "settle into place" rather than just a slide.
- Hover micro-interactions use plain Tailwind `group-hover:scale-110`/`group-hover:rotate-6` on icon badges (`GradientStatCard`'s corner icon, `Home.tsx`'s tahap link cards, `Sidebar.tsx`'s nav icons) rather than a custom keyframe — these are one-shot state changes tied to `:hover`, not loops, so they don't need `@keyframes` at all.
- `ChecklistSmkp.tsx`'s per-category `<details>`/`<summary>` accordion gained a chevron `<svg>` with `group-open:rotate-180` (the same open/closed indicator pattern `Bantuan.tsx`'s FAQ accordion already used) — previously this accordion gave no visual cue that a category could expand, or which ones were currently open.

**Icon badges on section/card titles**: this is applied exhaustively, not just to a few spots the first pass happened to touch — a follow-up round specifically went looking for every remaining plain-text heading after the first pass missed some. Every card/section/page heading that names a specific kind of data carries a small `h-6`–`h-8` square `bg-blue-50 text-blue-600` (or `bg-amber-100 text-amber-700` on an amber-tinted card) icon badge before the text, matching `StatTile`'s icon treatment: the 4 `LaporanUploadCard` titles, `EvaluasiCard`'s "Evaluasi Kinerja per Semester", `ChecklistSmkp.tsx`'s "Dokumen Legalitas (syarat wajib)" panel, "Rincian Skor per Kategori" title, the `LEGALITAS` category accordion, and its own "Total Skor"/"Persentase Kepatuhan"/"Layak untuk Pekerjaan Risiko" stat trio; `Show.tsx`'s "Dokumen & Laporan"/"Evaluasi Kinerja" `<h2>`s; `PlaceholderCard`'s sub-tahap mini-cards on `PersyaratanSeleksiPenetapan.tsx`/`TanggungJawabPemantauanPelaporan.tsx` (an `icon` prop, optional since `PlaceholderCard` is also used without one elsewhere); the blue info callout boxes on the Tahap 1/3 pages; `StatusStackedBar` and `AchievementBarChart`'s own titles; Beranda's "PJP Paling Perlu Perhatian" heading and the "belum lapor" reminder box; and `Sidebar.tsx`'s `SidebarSummary` "Total PJP"/"Perlu Perhatian" labels. `PageHeader` itself gained an optional `icon` prop rendered as a larger `h-10 w-10` badge next to the `<h1>`, wired on every page that uses it (each tahap page uses its own tahap icon, `Pjp/Index`+`Create`+`Edit`+`Show` use `building`, `Bantuan` uses `help`, `ChecklistSmkp` uses `persyaratan`). `LaporanUploadCard` picks its icon from a `jenis → icon name` map (`JENIS_ICON` in that file) rather than taking an icon prop, since the 4 `jenis` values are a fixed enum. `TahapIcons.tsx` gained `target` (a bullseye — the one icon defined as `<circle>` elements instead of a single `<path>`, so `TahapIcon`'s `{tahapIconPaths[name]}` must stay a plain JSX value, not assume `<path>` specifically), `calendar`, and `document` for this. Treat this as a standing rule, not a one-off pass: any new card/section/page heading that names a specific kind of data needs an icon badge too, on first add — don't wait for it to be flagged as missing again. `PjpFormFields.tsx`'s own field *labels* (not just card/section titles) followed the same instinct once flagged: a `FieldLabel` wrapper renders a small `h-4 w-4 text-slate-400` icon inline before each label (lighter-weight than the `bg-blue-50` badge used for card/section titles, since a form field label is a smaller, denser UI element) — `building`/`document`/`user`/`location`/`check`/`note` for Nama Perusahaan/NIB/Penanggung Jawab/Alamat/Status/Catatan respectively, adding 3 new icons (`user`, `location`, `note`) to `TahapIcons.tsx`.

**Demo data seeder**: `database/seeders/DemoDataSeeder.php` creates 7 fictional PJPs spread across all 3 status values and every achievement band on all 3 pages (including one PJP with zero laporan, to show the "belum ada laporan" null-state distinctly from a scored 0%) — purely so the app doesn't look empty when someone wants to see what it looks like populated. Deliberately **not** wired into `DatabaseSeeder::run()`, so a plain `php artisan migrate` / `db:seed` never creates fake companies by default; run it explicitly with `php artisan db:seed --class=DemoDataSeeder`. This data lives only in whatever SQLite file the command was run against — since each developer's/session's `database/database.sqlite` is a local, gitignored file, seeding it in one place (e.g. a cloud sandbox) never appears in another (e.g. the maintainer's own laptop); there is no shared database here, only shared code.

**Routing → controllers → Inertia pages** (see `routes/web.php`): each route renders a specific `resources/js/Pages/*.tsx` component by name (e.g. `Inertia::render('Pjp/Show', [...])` ↔ `resources/js/Pages/Pjp/Show.tsx`). There's no client-side routing; `TahapanController` has one method per page (Persyaratan/Tanggung Jawab/Evaluasi), each delegating to a shared `renderTahapan` helper so the "every PJP, with the right filters, status breakdown, and page-specific score" logic stays consistent across all three instead of being copy-pasted per page.

**File uploads**: `PjpLaporanController::store` saves to the `public` disk under `pjp-laporan/{pjp_id}/...` (served via the `storage:link` symlink) and creates the DB row in the same request. Deleting a `Pjp` (`PjpController::destroy`) explicitly deletes that whole storage subdirectory first — cascading DB deletes alone would silently orphan the files, since the FK `cascadeOnDelete()` only cleans up rows, not disk contents. Deleting a single `PjpLaporan` (`PjpLaporanController::destroy`) removes just that file. Both `update` and `destroy` on `PjpLaporanController` assert `$laporan->pjp_id === $pjp->id` (404 otherwise) to prevent cross-PJP ID-confusion via mismatched route params.

**Exports**: `GET /pjp/export` (query params: `search`/`status`, same as the index filters) streams an `.xlsx` via `App\Exports\PjpExport` (maatwebsite/excel — `FromCollection`/`WithHeadings`/`WithMapping`). `GET /pjp/{pjp}/export-pdf` renders `resources/views/pdf/pjp-report.blade.php` to PDF via `barryvdh/laravel-dompdf` (`Pdf::loadView(...)->stream(...)`) — this is the one Blade view in the app; everything else is Inertia/React. Both export routes are registered *before* `Route::resource('pjp', ...)` in `routes/web.php` because `/pjp/export` would otherwise be swallowed by the `GET /pjp/{pjp}` show route's route-model-binding.

**`BackButton`**: a plain `window.history.back()` button (`resources/js/Components/BackButton.tsx`), placed in the header action row of every page except `Home.tsx` (Beranda is the app's root — "back" has no destination from there) — `Pjp/Show.tsx`, `Pjp/Index.tsx`, all 3 tahap pages, and `Bantuan.tsx`. Deliberately real browser history rather than a hardcoded `href`: `Pjp/Show.tsx` in particular is reachable from many different places (any of the 3 tahap pages, `Pjp/Index.tsx`, Beranda's widgets), so there's no single correct fixed "back" target — history.back() always returns to wherever the reader actually came from. `Pjp/Create.tsx`/`Edit.tsx` don't get one since their existing "Batal" link already serves the same purpose for a form page, and `ChecklistSmkp.tsx` keeps its own pre-existing "Kembali" link (a fixed `href={`/pjp/${pjp.id}`}`) rather than switching to `BackButton`, since that page only ever has one logical parent.

**Frontend conventions**:
- Every page wraps its content in `<AppLayout>` (`resources/js/Layouts/AppLayout.tsx`), which renders `<Sidebar>` (nav + mobile hamburger drawer, active link matched by path prefix) and `<FlashMessage>`.
- `FlashMessage` listens to Inertia's `router.on('success', ...)` event rather than a `useEffect` keyed on the `flash` prop value — Inertia can hand back a referentially-identical-content `flash` object across two different visits, so a value-dependency effect misses a second identical success message in a row. If you touch flash-message behavior, keep the event-listener approach.
- Shared small components live in `resources/js/Components/`: `PjpFormFields` is the single source of truth for the create/edit form fields (`Pages/Pjp/Create.tsx` and `Edit.tsx` both wrap it — don't re-duplicate fields into the pages), `StatusStackedBar` renders the status-percentage bar chart (fixed color mapping: aktif=green, perlu_tindak_lanjut=amber, tidak_aktif=gray — status colors are intentionally not part of any generic categorical palette), `PjpFilters` is the search/status filter bar reused by `Pjp/Index.tsx` and each of the 3 tahap pages via `TahapanPjpSection` (no tahapan dropdown — that column no longer exists), `ConfirmDialog` replaces the browser's native `confirm()` for delete actions (controlled via local `useState<T | null>` holding the record pending deletion, not a boolean), `Pagination` renders a Laravel paginator's `links` array (used only by `Pjp/Index.tsx` currently).
- Every page sets its browser tab title via `<Head title="..." />` (`@inertiajs/react`) rendered as the first child inside `<AppLayout>`; the ` - Pemantauan & Pengelolaan PJP` suffix is appended centrally by the `title` callback in `resources/js/app.tsx`, so pass just the page-specific part (e.g. `"Data PJP"`, or a PJP's own name on `Pjp/Show.tsx`).
- `Pjp/Index.tsx` renders two parallel layouts for the same `pjps.data` — a `<table>` (`hidden md:block`) and a stacked card list (`md:hidden`) — instead of one responsive table, since an HTML table's columns don't collapse sensibly at phone widths. Keep both in sync if you change what's shown per row.
- `resources/js/types.ts` holds the shared TypeScript interfaces (`Pjp`, `PjpLaporan`) and option-label maps (`STATUS_OPTIONS`, `JENIS_LAPORAN_OPTIONS`, `KESESUAIAN_OPTIONS`) — keep these in sync with the PHP model constants (`Pjp::STATUS`, `PjpLaporan::JENIS`/`KESESUAIAN`) since nothing currently generates one from the other.
- Path alias `@/*` → `resources/js/*` (configured in both `tsconfig.json` and `vite.config.ts`).

## Known workarounds worth knowing about

`resources/js/app.tsx` casts the `createInertiaApp` `resolve`/`setup` config through `as never` — the installed `@inertiajs/react` (3.7.0) and `laravel-vite-plugin` (3.2.0) type definitions don't line up cleanly for the `resolvePageComponent` + `import.meta.glob` pattern under this TypeScript version (7.x, where `baseUrl` was also removed from `tsconfig` — paths must be written as `./resources/js/*`, not `resources/js/*`). This is a type-level workaround only; behavior matches the standard Inertia+Vite bootstrap.
